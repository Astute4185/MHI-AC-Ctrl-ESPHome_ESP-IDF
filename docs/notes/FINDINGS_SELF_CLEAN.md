# Self Clean Protocol Findings

## Status

Self Clean support is currently **feedback only**. The recurring 33-byte status path provides a strong state candidate, but the MISO command used to enable or disable Self Clean has not yet been identified.

Do not infer or fabricate a setter from the status fields.

## Observed 33-byte feedback

During the Clean test, recurring extended status changed as follows:

```text
DB7:  0x00 -> 0x02
DB13: 0x01 -> 0x05
```

The current candidate feedback bits are therefore:

```text
DB7[1]
DB13[2]
```

The Clean-related values persisted across subsequent operation-data traffic, supporting the interpretation that they represent persistent unit state rather than transient command noise.

When the AC turned off, the observed `DB13` value changed:

```text
0x05 -> 0x04
```

Self Clean remained active because bit 2 stayed set while bit 0 cleared. This is evidence that `DB13[0]` is unrelated to Self Clean. Shortly afterwards the Clean-related state cleared:

```text
DB7:  0x02 -> 0x00
DB13: 0x04 -> 0x00
```

## Current decoder rule

Neither candidate field is treated as canonical yet. The implementation keeps both raw candidate values and advances the public Self Clean state only when they agree:

```text
DB7[1] = 0, DB13[2] = 0 -> Self Clean OFF
DB7[1] = 1, DB13[2] = 1 -> Self Clean ON
mismatch                   -> keep last confirmed public state
```

This is an agreement-gating rule for provisional feedback. It is **not** a claim that the protocol permanently requires both bits to encode Self Clean. Further hardware captures may establish one field as canonical.

## Legacy MHI-AC-Trace capture

Reference: [absalom-muc/MHI-AC-Trace issue #2](https://github.com/absalom-muc/MHI-AC-Trace/issues/2)

The older capture records Self Clean with the legacy status `DB0` value changing from the normal Cool encoding to the Fan encoding. In the known 20-byte protocol, `DB0[4:2]` is the HVAC mode field. The change is therefore treated as the operating mode presented during the cleaning cycle, not as a dedicated Self Clean bit.

`DB0` must not be added as a third Self Clean candidate.

The same legacy capture does not identify a reliable Self Clean setter command. It is supporting behavioural evidence only.

## ESPHome behaviour

The entity is configured separately from climate presets:

```yaml
switch:
  - platform: MhiAcCtrl
    self_clean:
      name: Self Clean
```

Current behaviour:

- requires the 33-byte status path for feedback;
- publishes from observed hardware state only;
- does not assume `OFF` from an absent observation;
- ignores control writes because the setter is unknown;
- does not participate in command confirmation yet;
- remains independent from Normal, Eco, Hi Power, and ordinary HVAC mode selection.

## Unit-test coverage

The feedback decoder should retain these regressions:

```text
DB7[1] = 0, DB13[2] = 0 -> inactive
DB7[1] = 1, DB13[2] = 1 -> active
DB13 0x05 -> 0x04       -> remains active
legacy DB0 Fan change    -> not Self Clean feedback
```

## Remaining hardware validation

Run the following fixed-condition sequence:

```text
Clean OFF
Clean ON
Clean OFF
Clean ON
Clean OFF
```

Do not change these during the test:

- power;
- HVAC mode;
- fan;
- temperature;
- preset.

Confirm whether `DB7[1]` and `DB13[2]` always transition together. Preserve any disagreement captures because they are the evidence needed to choose a canonical feedback field.

Separately capture the controller/MISO traffic generated by dedicated Self Clean ON and OFF actions. The setter must be based on that capture rather than inferred from the MOSI feedback fields.

## Setter implementation gate

Do not add Self Clean command generation until the captured MISO request establishes:

- the command frame family;
- the write/set indicator, if any;
- the value encoding for ON and OFF;
- which returned field is authoritative for confirmation;
- any timing or polling required after transmission.

Once those are known, integrate the write through the existing command coordinator and use returned hardware state for confirmation, following the same architectural principles as Outdoor Unit Silent Mode without assuming the same bytes or timing.
